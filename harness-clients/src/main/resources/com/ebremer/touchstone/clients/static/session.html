Getting started
  1. Keep this page's address. It holds the session key: bookmark it to come back, and share it only with people who may control the session.
  2. Point your client at the storage, . It is the only URL your client should need: the storage's answers lead to everything else.
  3. Authenticate as alice, who owns the storage, or bob, in one of the four ways below. The quickest is a token from the identities table; the OpenID sign-in needs your client registered first.
  4. Use your client as you normally would, then work through the checklist. Each request is judged as it arrives, under Rules, and shows in the traffic log.
  5. Fix what fails, reset the results, and try again. When you are done, export the results: EARL for an implementation report, JUnit XML for CI, or JSON.

The guide Testing a client explains each step in detail.

Connect your client

This session fronts , a real server behind the proxy. Your client talks to that server through the storage URL below, and the session records and judges every request as it would its own storage's.

  • The server is as it is: the session sets no traps, and a task's fault is one the proxy injects itself ().
  • Rules that need what only the session's own servers know, such as the details of a credential or a notification's signature, are inapplicable.
  • The server decides whom to trust. alice and bob, below, work if it trusts their identity documents and the session's OpenID Provider; otherwise use identities it knows.

Identities

Your client can authenticate as alice or bob in four ways. It can sign in at the session's OpenID Provider with a username and password, after you register it below. It can sign a credential itself with the identity's key, as the CID suite describes: sub, iss and client_id are the WebID, and kid names the verification method. It can present a SAML 2.0 assertion from the session's identity provider, which this page or the session API hands out, base64url-encoded, with the token type urn:ietf:params:oauth:token-type:saml2. Or it can use a token from this page, for a client without authentication yet.

Register your client with the OpenID Provider

For the OpenID sign-in, register the redirect URIs your client uses. A redirect URI must match exactly, except that one on http://127.0.0.1 or http://[::1] may use any port. Leave the client ID empty to be given one.

      Checklist

      Most rules judge whatever your client does. These need you to do something on purpose: start the task, then do what it says with your client. A task that arms a fault makes the session answer one request differently, as a server may, to see how your client copes. The order does not matter, and you can start a task again.

      Rules

      A rule passes once a request has tried it and none has failed it. A failure keeps the first offending request; untested means your client has not done what the rule is about yet. Only MUST rules decide the verdict: SHOULD failures are warnings, and MAY rules are information.
