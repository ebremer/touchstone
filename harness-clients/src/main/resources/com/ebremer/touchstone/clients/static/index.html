Touchstone client sessions

Test an LWS client against a storage of your own. Start a session, point your client at its storage URL, and watch each request it sends judged against the client requirements of the W3C Linked Web Storage drafts. When you are done, export the results as EARL, JUnit XML or JSON.

Start a session

Naming your client is optional. The name, version and homepage become the subject of the reports you export, and you can change them later.

Areas to test

The rules of an area you leave out show as inapplicable.

Server

A proxy target is a real server behind this service. Your client talks to it through the proxy, and the rules that need the session's own servers are inapplicable. One session holds a target at a time.

How it works

  1. Start a session. It opens on its own page, whose address holds the session's key. Bookmark it to come back, and keep it to yourself: whoever has it controls the session.
  2. Point your client at the storage URL the page shows. The storage asks for authentication the way an LWS storage does. Your client can act as alice, who owns it, or as bob, and has four ways to authenticate: an OpenID sign-in, a key to sign its own credentials with, a SAML assertion, or a ready-made access token.
  3. Use your client as you normally would. Each request is judged as it arrives, and the traffic log shows it as the server saw it. Then work through the checklist: some rules need you to do something on purpose, and some tasks make the session refuse a request once, to see how your client copes.
  4. Read the results. Every failure shows the request, the clause it breaks with a link to the specification, what was expected against what was sent, and how to fix it.
  5. Fix, reset, repeat, then export the results as EARL (for implementation reports), JUnit XML (for CI) or JSON.

The guide Testing a client explains each step in detail.

What you get

  • A storage, its authorization server and an OpenID Provider, private to your session, with two identities: alice, who owns the storage, and bob.
  • A page that records every request your client sends and the rules it passed or failed.
  • Tasks for the rules that need you to do something on purpose.
  • Signed notifications to your client's inbox, which must be a public https URL, and on request forged ones, to see that your inbox verifies what it receives.

The storage behaves as the LWS drafts allow, which is not always what a client expects: page and linkset URLs are opaque, resource URLs do not mirror their containers, binary resources refuse PUT, the search index lags a little, and one resource in the root container is a decoy that challenges with a realm that does not contain it.

From a script or CI

Everything the page does is plain HTTP, so your client's own test suite can drive a session:

curl -s -X POST …/sessions \
  -H 'Content-Type: application/json' \
  -d '{"clientUnderTest": {"name": "My LWS client", "version": "0.3.1"}}'

The answer holds the storage URL, access tokens for alice and bob, and the session key, which the session API takes as a Bearer token. Run your tests against the storage, then fetch results?format=junit and fail the build on a MUST failure.

Limits

A session ends after two idle hours, or a day at most. Everything lives in memory and is gone when the session ends; keep what you need by exporting it. Request bodies are capped at 1 MiB, and each session at 500 resources. Credentials never show in the log, only a fingerprint of each.
